MERGE 客户合并 · 触发条件与全流程教程

本文档基于 2026-09-21 的真实端到端走查（截图均为实际运行画面），讲解系统在哪些情况下会触发 MERGE、以及合并审批如何流转与生效。

一、什么情况会触发 MERGE

触发场景条件系统行为
① 单条创建命中疑似重复
Duplicate Check		 新建客户提交时，客户法定名称与存量主档相同（信用代码不同）；且与候选主档归属 BU 不同（跨BU） 新主档 match_state=SUSPECTED；自动生成跨BU治理任务（CROSS_BU / 风险 High / 72h SLA，备注「需 GC Scope 决策」）
② 单条创建命中精准重复 统一社会信用代码与存量 active 主档相同（EXACT） match_state=EXACT；创建审批批准后自动关联到存量 One ID，不新建主档
③ 批量导入 Suspected 行跨BU命中 批量上传批次中某行判定为疑似重复，且命中的存量主档与批次 BU 不同 该行升级为 MERGE 审批（bizType=IMPORT 的行级合并模式），批准后执行行级 LINK
④ 手动发起合并
治理中心		 在客户主档详情点「发起合并」，选择要并入的目标 One ID 生成 bizType=MERGE 审批待办（AP-…），跨BU 时风险 High；批准到「结束」即执行合并

同名 ≠ 同客户：仅名称相同判为 SUSPECTED（人工决策）；信用代码相同判为 EXACT（系统强证据）。跨BU 疑似重复必须由 GC Scope 级别决策，这是主数据治理的核心管控点。

六、疑似重复的审批动作（对齐总设计，2026-09-21 更新）

按总设计 V6.1，疑似重复的审批任务不再提供普通「批准 / 拒绝」，必须做出合并方向的决策：

节点动作集说明
BU Scope 初审（跨BU）升级GC决策 / 排除重复 / 退回补充BU 无权跨BU合并，只能升级、排除或退回
BU Scope（同名BU）确认合并 / 排除重复·继续新建 / 退回补充Same-BU 由 BU 直接决策
GC Scope 决策确认关联已有 / 创建新主档 / 退回BU修复跨BU最终决策权在 GC
MERGE 合并审批确认合并 / 拒绝合并 / 退回BU合并待办专用动作集

七、合并目标候选收敛（只列重复候选）

发起合并弹窗的「合并目标」下拉只列出与源客户构成重复命中的存量主档（同名或同信用代码），并标注命中原因；不再列出全部客户。无候选时下拉禁用并提示「未发现重复候选」。

说明：「发起合并」入口仅对 active 主档开放——pending 客户的重复决策在审批任务里完成（升级GC / 排除 / 确认关联已有），active 存量之间的重复才走 MERGE 审批。

六、你可以自己动手验证的路径

  1. 触发疑似重复：Business User → 新建客户，名称填「上海清视眼镜有限公司」+ 新信用代码 → 提交后到数据库看 cmd_customer.match_state 与 cmd_governance_task。
  2. 触发精准重复：新建客户时信用代码直接填存量值 91310000672670432F（GC-000001）→ EXACT，批准后自动关联。
  3. 手动合并：任一同名客户详情 →「发起合并」→ Steward 审批批准 → 观察状态与合并记录。
  4. 批量导入：上传含同名不同码客户的 Excel → Suspected 行跨BU时在批量治理中升级合并审批。
