ESSILOR · CMD POC

批量导入功能 · 操作手册

面向不熟悉业务的同事：从「为什么要做批量导入」讲起，到每一步点哪里、填什么、会看到什么，全部配图说明。跟着本手册走一遍，就能完整掌握这条流程。

依据：Essilor CMD POC 总体设计方案 V6.1「场景二 批量导入」 截图：24 张（真实系统实拍） 环境：http://localhost/cmd-poc/login

一这个功能解决什么问题

Essilor 的客户主数据分散在多个系统里（DMS+、SAP、云端、人工登记）。当某家门店、经销商或集团客户成批出现时，业务同事手里往往是一个 Excel 名单——几十到几百行。如果靠人工一条一条录进主数据系统，会遇到三个必须解决的问题：

① 重复

同一家公司可能在别的系统里已经存在。盲目新建就会产生两条主档，后续对账、发货、报表全部出错。

② 脏数据

Excel 是人工填的：少了地址、信用代码位数不对、名字写成简称。这些行不能进主档，必须退回给填表人修改。

③ 责任

"新建一条客户主档"是有后果的动作，需要数据管家（Steward）确认、走审批，不能由导入动作自动生效。

系统的解法：把"上传"拆成 6 道关卡

1 文件级预检→ 2 行级 DQ 校验→ 3 批次内去重→ 4 存量匹配分流→ 5 人工治理→ 6 审批发布

每一行数据都会被系统打上一个结论，叫「结果分流」，只有四类：

分流结果含义（用大白话讲）系统会怎么处理责任人
Exact 精确匹配 这行数据和主档里某条客户是同一家（信用代码一模一样） 自动关联到已有的 One ID，不新建 系统自动
Suspected 疑似重复 "看起来像同一家，但不敢确定"——名称一样但信用代码不同，或者同一批里出现两次 停下来，等数据管家人工判断：关联、退回还是排除 BU / GC Steward
New 新增 主档里确实没有这家公司，是真正的新客户 发起「批量导入确认」审批，审批通过后自动生成 One ID Steward 审批
Invalid 无效 必填项缺了，或者信用代码格式不对（比如不是 18 位） 退回修复，请填表人改好后重新上传 Business User
一句话理解 Excel 里的每一行，最后一定会落到这四个桶之一。你的工作就是把 Suspected 那个桶清空，然后让 New 那个桶走完审批。

三整体流程一览

这条流程在系统里被建模成一个正式的工作流，叫 IMPORT_BATCH（批量导入确认）。它有 7 个阶段、5 条泳道、10 个节点：

阶段阶段名泳道（谁做）节点
1发起Business User提交业务申请
2数据准备系统自动处理数据装配
3自动校验系统自动处理自动校验（DQ）
4匹配分流系统自动处理条件分流（四类）
5人工治理Data Steward BU Scope
Data Steward GC Scope		BU Scope 初审 → GC Scope 决策
6审批发布Platform Admin发布下游 → 执行与生效
7追踪审计Auditor（只读）审计留痕
重要：前 4 个阶段是"一瞬间"完成的 你在点下「提交」按钮的一瞬间，系统就把预检、DQ、去重、匹配全部跑完了，直接给你结果。第 5、6 阶段才需要人参与。

「模板表头（5 列，标 * 为必填）」这行是干什么的？ 它把本次要用的模板需要哪些列、哪些是必填直接摆在你眼前：CustomerName* CreditCode* Address* City ContactPhone。 上传前对照自己的 Excel 表头看一眼，就能避免"表头缺列导致整批退回"。

5 选择要上传的 Excel Business User

在 「上传 Excel / CSV」 区域，把 Excel 拖进去，或者点一下区域选文件。选好后会显示文件名与大小：

为什么文件行数这里不显示？ 浏览器端不解析 Excel 内容（避免大文件卡顿），行数与表头的校验统一在提交后的文件级预检完成——预检通过才建任务，不通过整批退回，所以不会产生"半截数据"。
限制与建议 单文件不超过 10MB；格式支持 .xlsx / .xls / .csv。表头行必须是第 1 行，数据从第 2 行开始。
6 提交 Business User

点右下角蓝色 「提交」。系统在后台一次性跑完前 4 个阶段，几秒后弹窗自动关闭、列表刷新，最上方出现刚创建的任务：

为什么状态是「Partial Success」而不是「Completed」？ 因为 5 行里有 1 行是 Invalid。只要存在坏行，就说明"这一批只成功了一部分"，系统如实标成部分成功。这是设计上的刻意选择——不掩盖问题。

如果表头不对会怎样？

整批退回，连任务都不会创建，页面弹出红色提示：

示例提示文案 文件预检未通过：表头缺少列 Address，已整批退回（请使用最新模板填写）

遇到这种提示，回到步骤 3 重新下载模板，把数据填进正确的列再上传。

7 查看结果分流 Business User

在任务列表那一行，点操作列的 「查看结果」：

弹窗有三层信息，从上到下读：

  1. KPI 卡片：1 Exact 2 Suspected 1 New 1 Invalid（另有 Review 用于规则/业务复核）。每张卡片都能点，点了下方明细就切换到这一类。
  2. 处理方式路由表：一眼看清"谁负责哪一类"——Exact 由系统自动关联、Suspected 由 BU/GC Steward 人工治理、New 由 Steward 审批后生成 One ID、Invalid 由 Business User 退回修复。
  3. 明细区：显示当前选中分流的每一行，含行号、客户名称、信用代码、One ID / 候选、质量分、问题说明；如果是 Suspected，还有一列 治理操作。
8 逐个下钻四类明细 Business User

点任意一个 KPI 卡片，下方明细就换成那一类。四个都点一遍，就能看懂这批数据的全貌。

① 点 Exact —— 看清楚"哪几行已经认到老客户了"

② 点 Suspected —— 这是你要干活的地方

③ 点 New —— 将来会变成新客户的行

④ 点 Invalid —— 需要改 Excel 的行

9 治理疑似行（三个按钮） Business User / Steward

回到 Suspected 明细，对每一行做一个判断。三个按钮的含义：

按钮你什么时候点它系统做了什么结果
关联已有 确认这行和主档里某家公司就是同一家，把它挂过去 弹窗让你输入 / 修改 One ID，确认后把该行改成 Exact Suspected → Exact
退回修复 线下核实后发现数据有问题，需要填表人改 把该行标为退回，注明"需线下核实后再导入" → Invalid（Fix）
排除 这行不该进主档（例如测试数据、已停业客户） 把该行标为排除，注明"不纳入主档" → Invalid（Ignored）

13 批准并发布 Steward BU

在「审批意见」框里填一句说明，然后点 「批准」：

批准后系统立刻执行发布动作，待办数量随之变化：

批准的一瞬间，系统背后做了三件事
  1. 为所有 New 行生成客户主档，分配 One ID，状态设为 active，来源系统标为 IMPORT（可追溯回这次导入）；
  2. 把导入任务状态改成 Completed，并在备注里写上"审批通过：N 条 New 行已生成 One ID（审批人：xxx）"；
  3. 把审批意见、操作人、时间写入审批轨迹与审计日志。

五四类分流判定规则（系统怎么想的）

很多人会问"为什么这行被判成 Suspected 而不是 New"。系统的判定是有严格顺序的，从上往下第一个命中的就是结论：

顺序判断条件结论
1必填列有缺失，或信用代码不是 18 位大写字母数字Invalid
2与本批前面某行的信用代码重复Suspected
3与本批前面某行的客户名称重复Suspected
4信用代码在现有 active 主档里命中Exact（带出已有 One ID）
5客户名称与现有主档相同（但信用代码不同）Suspected（带出候选 One ID）
6以上都没命中New

任务状态是怎么推出来的

条件任务状态
全部行都是 InvalidFailed（失败）
有 Invalid，也有其他Partial Success（部分成功）
没有 Invalid，但有 Suspected / NewWaiting for Review（待复核）
全部是 ExactCompleted（完成）

行级质量分（DQ Score）

每行从 100 分起算，每发现一个问题扣 20 分；被判为 Invalid 的行保底 40 分。所以「质量分」列可以直接当"这行有多干净"的指标看。

七常见问题

Q1. 提交后什么都没发生，或者列表里还是空的？

依次检查：① 是不是在批量导入菜单下（不是工作台）；② 页面右上角有没有红色报错提示；③ 后端服务是否在运行（浏览器控制台若出现 502，说明后端没起来）。

Q2. 提示「文件预检未通过：表头缺少列 XXX」怎么办？

你上传的 Excel 表头与模板不一致。回到「下载模板」，用新下载的模板重新粘贴数据，确保表头是 CustomerName / CreditCode / Address / City / ContactPhone（注意大小写和不要有空格）。

Q3. 明明是新客户，为什么被判成 Suspected？

最常见的原因是名称与存量客户完全一样。系统的逻辑是：名称一样但信用代码不同 → 不敢认定是新客户，先让人确认。这正是为了避免重复建主档。如果确认确实不是同一家（例如同名不同地区），在治理里点「排除」或「退回修复」并注明原因即可。

Q4. New 行什么时候才会真的变成客户？

必须等 Data Steward 在「治理与审批」里点「批准」。批准前它只是"待生成"，主档里查不到。批准后系统会分配 One ID，状态为 active，来源系统记为 IMPORT，并可通过任务的 Job ID 追溯。

Q5. Invalid 的行怎么处理？

这行不会进主档。你需要打开原始 Excel 修改对应行（补齐必填项、修正信用代码），然后把修好的行放在一个新文件里重新提交一次导入。原任务保留为历史记录。

Q6. 怎么知道谁在什么时候改了什么？

每个动作都会留痕：行治理动作写审计事件（事件类型 IMPORT），审批动作写审批轨迹，流程节点写工作流步骤日志。用 Auditor 账号进入 审计中心 / 治理审计 可以查询，或在「流程跟踪」弹窗中查看该次执行的上下文与节点明细。

Q7. 「Suspected」和「Review」有什么区别？

Suspected 是"疑似重复"，由匹配规则自动得出，交给 BU/GC Steward 治理；Review 是"规则或业务复核"，用于需要人工按规则确认的场景。本次演示数据没有产生 Review 行，所以卡片显示为 0。

附一页纸总结

Business User 上传 Excel→ 系统自动预检/校验/去重/匹配→ 四类分流
├─Exact 自动关联，无需操作
├─Suspected → 治理：关联已有 / 退回修复 / 排除
├─New → BU Steward 审批通过 → 生成 One ID
└─Invalid → 改好 Excel 重新上传

需要人动手的只有两处：①把 Suspected 清空、②让 New 走完审批。其余全部由系统自动完成。
