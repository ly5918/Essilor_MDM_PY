1三分钟看懂这个系统

先建立整体印象，细节后面再讲。

这个系统叫 CMD（Customer Master Data，客户主数据管理）。它解决的问题是： 同一个客户，在不同的业务系统里有不同的名字和编码，导致对不上账。

系统做三件事：① 把散落的客户信息收进来 → ② 判断它是不是重复的 → ③ 给它一个终身不变的身份（One ID）， 并纳入客户层级，之后所有变更都留痕。

三条主线业务

故事一 · 单条创建

业务员新建一个客户，上传营业执照，系统 OCR 自动填空，跑数据质量打分和查重， 然后 BU 初审 → GC 决策，通过后成为主数据。

故事二 · 批量导入

把 Excel/CSV 丢进来，系统逐行检查质量、批内去重、跟存量比对， 分四类结果：可入库 / 疑似重复 / 需修复 / 拒收。

故事三 · 变更与治理

改名、改地址要走审批；客户不合作了要「逻辑停用」（不物理删除）， 全程保留 Before / After 和审批轨迹，审计随时可查。

一句话记住 客户管理 = 一条条具体的客户记录；客户层级 = 这些客户之间的上下级关系（谁属于谁）。 两者合起来，才是客户主数据的完整视图。

3界面导览：屏幕上每块是什么

整个系统只有一套骨架，学会一次就够用所有页面。

① 顶栏

  • 左侧：折叠/展开菜单
  • 中间：模拟角色下拉（切换身份）
  • 右侧：头像 → 布局设置 / 退出登录

② 左侧菜单

按角色显示可用功能。带数字小徽标的表示有待办（如「治理与审批 8」）。 「流程中心」是可以展开的二级菜单（下含「已激活工作流」「已完成的工作流」两个子菜单）。

③ 标签页

你打开过的页面会排成标签，可以来回切换、单独关闭，不用退回菜单重新点。 最右侧可一键关掉全部。

④ 内容区

页面主体。统一结构是：H2 标题 + 一句说明 + 操作按钮， 下面是卡片分区，卡片里通常是表格或指标。

一个规律 每个页面顶部的 H2 标题和它右边的一句小字，就是这一页的「说明书」。 忘了这页干什么，看那行小字最快。

5每个菜单是什么（逐页说明 + 截图）

按角色分组。图片都是真实运行截图，可以直接对照你自己的屏幕。

5.1 Business User（业务用户）

工作台

第一屏。显示你的 Scope、待办数量、快捷入口。点卡片能直接跳到对应功能。

客户管理

客户列表（含 One ID、名称、BU、状态、层级）。可搜索、查看详情、新建客户、查看 OCR 识别结果。

批量导入

先选模板下载，填好再上传；系统按行检查质量与重复，结果分四类展示。

客户层级

左：搜索 + 待归位主数据；中：A3-A2-A1 层级树；右：节点详情。可发起层级关系申请。

变更与停用

发起关键属性变更申请，或对不再合作的客户做逻辑停用。都能看到 Before / After。

流程中心

运行态二级菜单，5 个角色都有，含 2 项：已激活工作流（引擎实例已启动、还没跑完的单子）、已完成的工作流（已结束实例的列表）。某一单的完整链路不再单占一个菜单——点列表行内的「查看流程跟踪」弹出窗口，窗口里还能逐节点点开看明细。（工作流定义不在这里——那是配置态，归 Platform Admin 的「平台管理 → Workflow」。）

5.2 Steward BU（BU 数据管家）

工作台

BU 范围治理视角：本 BU 申请初审、异常治理、SLA 管理。

治理与审批 重点

审批队列（KPI + Tab + 筛选）。本 BU 审批、DQ 复核、疑似重复、层级与批量治理在这里统一处理。

客户主档

与「客户管理」同一份数据，但按 BU 管家的权限和视角呈现。

客户层级 归位入口

除了看树，左栏「待归位主数据」区每个客户后面有「归位」按钮，把批准后的主数据挂进层级树。

批量治理

处理批量导入产生的异常行（修复后重跑）。

变更与停用

审批业务用户提交的变更 / 停用申请。

5.3 Steward GC（GC 数据管家）

5.4 Platform Admin（平台管理员）

Workflow（工作流定义）也在这一页：点「平台管理 → Workflow 卡片 → 管理」进去， 就能看到系统里全部 CMD 业务工作流——场景编码 ↔ Warm-Flow 流程名 / 流程编码 / SLA / 版本 / 泳道节点数 / 部署状态， 每行还可以「配置」（打开该场景的 Workflow 配置弹窗）或看「泳道图」（图形化流程蓝图）。 这是配置态能力，只有 Platform Admin 有，业务角色不需要也不应该改流程定义。

页面顶部固定一条口径说明，弹窗里每一行节点也都带「平台固定 / 可配置」标签，什么不能改、什么能改一目了然：

  • 平台固定（不可修改）：场景编码、流程编码（与 Warm-Flow 流程定义、引擎节点定位绑定）、 业务入口与录入节点、OCR / DQ / Duplicate Check / One ID 等系统自动节点、发布与运行追踪、审计证据链， 以及主干 BU 初审（可改命中条件与办理角色，但不可停用）。
  • 按场景可配置：节点路由规则（可新增 / 停用，即增删工作流项目）、命中条件表达式、 办理角色、会签 or 或签、节点 SLA、场景 SLA、超时动作与超时升级、邮件通知方式与通知对象、 以及 GC 决策节点是否启用（V6.1 待确认项：High End 必经、Mainstream 可只走 BU 初审）。

配置弹窗共 4 个页签：流程节点（11 个泳道节点蓝图 + 可编辑的节点路由规则表）、 路由条件（场景启动条件 + 当前节点命中条件 + 可用路由变量）、 SLA 与升级、版本与发布。配置真的会落库—— 保存后写入平台配置表（场景表 + 节点审批人规则表），下一次流程实例启动即按新配置路由。 图形化的流程设计统一由「泳道图」承载，所以配置弹窗里不再重复画一遍阶段链。

子菜单看什么

6手把手：走完一条完整业务

跟着做一遍，你就掌握这个系统 80% 的用法了。

先看懂这条链

新建客户→ OCR 识别→ DQ 打分→ 查重→ 提交申请→ BU 初审→ GC 决策→ 成为主数据

绿色 = 系统自动跑完 橙色 = 需要人点一下 蓝色 = 用户操作

Step 1 · 以 Business User 登录，进入「客户管理」

  1. 登录：登录页点 Business User，再点「使用 Microsoft 账号登录」。成功后顶栏会显示 Business User 工作台。
  2. 点左菜单「客户管理」：看到客户列表，含 One ID、客户名称、BU、层级归属、来源、状态等列。「层级归属」列显示 A1/A2/A3 说明已归位；显示「未挂载」说明还没进层级树。
  3. 点「新建客户」按钮：弹出「新建客户申请」表单。

Step 2 · 上传营业执照，让系统自动填

  1. 在弹窗里点上传营业执照：选一张测试素材（docs/cmd-poc/测试素材/营业执照/license_0x.png）。
  2. 点「查看 OCR 识别结果」：弹出识别结果，显示每个字段的识别值和置信度。POC 环境按文件名匹配预置结果，不会真的调外部 OCR 服务。
  3. 点「写回表单」：弹窗关闭，表单里对应字段被自动填好，字段名旁边会出现绿色 OCR 回填 标记。这个标记很重要——它告诉你哪些值是系统给的，需要人工再核对。

Step 3 · 补全后提交，看系统自动做了什么

  1. 补全必填项：客户法定名称、注册地址、省市、联系人、电话。如果直接点「提交申请」而不填，系统会逐个字段报红提示——这就是下面的图 6A。
  2. 点「提交申请」：系统立刻做三件事：
    • 生成 One ID（终身身份）和 申请编号（如 AP-20260920-0001）
    • 跑 DQ 质量打分：缺统一社会信用代码 -12、缺地址 -8、缺省市 -4、缺联系人 -4、缺电话 -4；≥90 判 A、≥75 判 B、≥60 判 C，低于 60 标记 High risk
    • 自动跑完 OCR / DQ / 查重 三个节点，并创建审批任务
  3. 看提示：成功后弹出回执，含 One ID 与申请编号；客户列表刷新，新申请出现在列表里。

Step 4 · 出错时会看到什么

看到红色报错不要慌 先读提示文字，它通常已经告诉你怎么改。比如「层级最多 3 级（A3 → A2 → A1），xx 已是末端节点，不能再挂下级」 意思就是：你选的上级已经在最底层了，换一个上级即可。

Step 5 · 换成 Steward BU，审批这单

  1. 右上角「模拟角色」选 Data Steward · BU Scope：左侧菜单立刻变成 BU 管家的。
  2. 点「治理与审批」：在队列里找到刚提交的那单（可按 One ID / 申请编号搜）。
  3. 点任务编号打开审批详情：右侧能看到泳道图、Data context state、审批轨迹。
  4. 点「批准」或「升级 GC」：
    • 点批准 → 客户状态变为 active，正式成为主数据，流程结束
    • 点升级 GC → 流转到 GC 决策节点，需要 GC 管家再点一次
    • 点拒绝 → 客户状态 rejected，流程终止
    • 点退回补充 → 客户状态 returned，退回给申请人补材料

Step 6 · 客户层级里「归位」（关键一步，详见第 8 章）

  1. 点左菜单「客户层级」
  2. 看左栏「待归位主数据」：刚批准的那个客户已经在列表里了。批准后系统会自动把它登记成「待归位」节点，所以它一定会出现在这里。
  3. 点该客户后面的「归位」按钮：弹出「主数据归位」窗口。
  4. 选目标父节点：只能选 A3（集团）或 A2（主账户）。系统会实时告诉你归位后是什么级别、完整路径是什么。
  5. 点「确认归位」：系统一次做完五件事：环路检测 → 级别推导 → 完整路径重建 → 祖先节点计数刷新 → 层级关系留痕。
  6. 回中间层级树看：新节点已经挂在树上了。回到「客户管理」，该客户「层级」列也从「未挂载」变成了 A1。

7六个核心概念

把这几句话记牢，后面看任何页面都不会迷路。

概念是什么关键规则
One ID 客户的终身身份编码，形如 GC-23F62B7A 一旦生成，终身不变。改名、改地址、合并都不会重新生成。所有列表都能用它搜。
申请编号 一次审批流程的单号，形如 AP-20260920-0001 一个客户可能有多条申请（新建、变更、停用），每条一个编号。追流程用这个。
主数据 / 黄金记录 审批通过、状态为 active 的客户 只有主数据才能被下游系统消费。「客户管理」里看到的就是主数据 + 在途申请。
客户层级 A3-A2-A1 A3 = 集团 / 法人实体，A2 = 主账户，A1 = 门店 / 终端 最多三级。级别由父节点自动推导，系统不做人工指定。层级由 Data Steward 治理。
待归位主数据 已批准成为主数据、但还没挂进层级树的客户 批准后自动登记。它只出现在「客户层级」页左栏，不进中间那棵树。
Loop Check（环路检测） 防止层级关系成环 如果把某个节点挂到它自己的后代下面，系统会直接拒绝并给出冲突路径。
为什么不物理删除？ 客户数据被下游系统引用过，删掉会造成对不上账。所以系统只做逻辑停用（状态变 inactive） 或归档，历史记录和 Before / After 全部保留，审计随时可查。

8「批准成主数据后，客户层级里为什么看不到？」

这是最容易困惑的一点。答案是：它已经进去了，只是停在「待归位」区，等着被归位。

8.1 先理解为什么要有这一步

「批准」解决的是这个客户存不存在、数据可不可信； 「归位」解决的是这个客户在集团的哪个位置、归谁管。这是两件不同的事，由两个角色负责：

审批（Steward BU / GC）

判断这条客户数据是否可信、是否与已有客户重复。通过 → 拿到 One ID，成为主数据。

归位（Data Steward）

判断这个客户在 A3-A2-A1 里该挂在哪个上级之下。这个过程必须由人治理，不能系统乱猜。

所以系统的做法是两段式：批准的那一刻，先把客户登记进层级体系（变成「待归位」节点）， 保证它不会漏；再由管家把它挂到正确的位置。这样既做到了「批准即纳入体系」，又守住了「层级必须被治理」的原则。

8.2 在哪看？怎么看？

打开 客户层级 页，页面顶部有一行绿色说明条，写着当前有几个待归位；左栏下半部分就是待归位列表。

8.3 一句话回答客户/评审的提问

「批准后客户在哪儿？」 批准后它立刻出现在两个地方：① 客户管理 / 客户主档列表里（状态 active，拿到 One ID）； ② 客户层级页左栏的「待归位主数据」里。 等 Data Steward 把它归位到 A3-A2-A1 之后，它才出现在中间的层级树上。 两者合起来才是主数据的完整视图。

9常见问题 FAQ

点开看答案。

为什么我看到的菜单比别人的少？
菜单是按角色下发的。Business User 看不到「治理与审批」，Auditor 只有只读页面。 想换视角，用右上角「模拟角色」下拉切换。
同一个客户怎么有好几条记录？
大概率是还没合并的疑似重复。系统在「治理与审批」里把它们标成 SUSPECTED， 需要 GC 管家核对匹配证据后决定：合并到已有 One ID，还是确认为新客户。 合并时源记录不会删除，而是保留 Source Snapshot 和映射关系。
为什么「客户层级」页在某些屏幕上变成了上下三块？
这是刻意做的响应式适配。窗口宽度 ≤ 1280px 时，左/中/右三栏会折成上下三块， 避免三栏硬挤在一起看不清。把浏览器窗口拉宽就会恢复成并排三栏。
提交申请时提示「请输入客户法定名称」怎么办？
这是字段级校验，说明必填项还没填。看输入框下方的红色小字，它直接告诉你是哪个字段缺了。 补上之后提示会自动消失。
归位时报「层级最多 3 级……已是末端节点」怎么办？
你选的父节点已经是 A1（最底层），A1 下面不能再挂东西。 改成选一个 A3 或 A2 作为父节点即可。系统这样限制是为了保证层级永远是 A3 → A2 → A1 三级。
「泳道图」和「流程跟踪」有什么区别？
两个不同的可视化，用途不同，但都是弹窗（不再单独占菜单）：
· 泳道图（V6.1）：横向 7 个业务阶段、纵向 6 条角色泳道，看「这类流程长什么样 / 这单走到哪一步」。入口在「流程跟踪」弹窗内的「泳道图」按钮（列表里点 One ID 也可直接打开）。
· 流程跟踪：Warm-Flow 引擎的真实实例视图 + 11 步泳道步骤条 + 步骤明细 + Data context state + 审批轨迹 + 引擎关联。入口有二（都是同一个窗口，不会各做一套）：①「已激活工作流」/「已完成的工作流」行内「流程跟踪」；②审批详情右侧「流程跟踪」按钮。
· 步骤明细是流程跟踪的精华：点步骤条上任意一步，下方立刻换成那一步的内容（如「OCR 与智能补全」列出识别出的字段，「DQ 质量校验」给出得分与命中项、扣分原因）。
POC 环境和正式环境的差别？
POC 阶段为了演示顺畅，做了这些简化：/cmd/** 接口免登录（正式上线前删除白名单）、 OCR 用预置结果不调外部服务、AAD 单点登录用模拟账号替代。 数据结构、审批流、层级治理逻辑都是真实可跑的。

10现场演示话术建议

如果要给别人演示，按这个顺序讲最顺。

  1. 先讲问题，再讲系统 「同一个客户在 Cloud、DMS+、SAP 里分别叫三个名字、有三个编码，报表对不上账。我们要解决的就是这个。」
  2. 用「故事一」走完整链路 新建 → OCR → DQ → 提交 → BU 初审 → GC 决策 → 成为主数据。中途故意留一个必填项不填，让它报红，展示校验在做实事。
  3. 在「流程跟踪」里指出 One ID 「这个编码在客户管理、审批任务、层级、审计日志里是同一个值，任何一处都能拿着它查出全链路。」
  4. 切到 Steward BU，做「归位」这一步 这是最容易被问到的一环：批准 ≠ 自动挂层级。先展示待归位列表，再点归位、看预检、确认，最后回层级树看新节点和祖先计数变化。
  5. 切到 Auditor 收尾 「刚才所有动作都被记下来了：谁、什么时候、改了什么、Before / After 是什么。而且全程没有任何物理删除。」
  6. 最后讲配置能力（Platform Admin） 字段、DQ 规则、匹配规则、模板、Workflow 都是配置驱动、版本化的，不用改代码。
三个最能加分的细节 ① 打开「层级归位预检」，让客户看到系统在提交前就把环路、级别、完整路径算给你看； ② 打开「流程跟踪」窗口，指出自动节点（OCR/DQ/查重）是一起变绿的、人工节点是一步一步亮的，再点开任意一步看它的明细； ③ 打开「审计中心」，随便挑一条记录展开 Before / After。
