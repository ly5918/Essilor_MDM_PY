1. 前置知识（5 分钟）

这套系统叫 CMD（Customer Master Data），目标是为依视路全球客户建立“一个客户、一个主数据记录”。下面几个名词贯穿所有操作：

名词白话解释在系统里对应哪里
One ID 客户的“身份证号”，全球唯一。一个客户在不同 BU、不同来源系统可能有很多本地编码，但 One ID 只有一个。 客户列表的 One ID 列，例如 GC-73CE714B
BU / Scope Business Unit，业务单元。POC 里用 High End / Mainstream / Frame / Sun 等区分数据权限。 新建客户表单里的 BU、Product Line、Source System
Data Steward 数据治理员。分 BU Scope（只看本 BU）和 GC Scope（跨 BU 全局决策）。 登录角色里的 bu / gc
DQ（Data Quality） 数据质量打分。缺字段会扣分，最终分为 A/B/C/D。 客户列表 DQ 列、审批任务 DQ 列
Duplicate Check 查重。系统按信用代码、地址、名称等判断这是新客户，还是和已有客户重复。 审批任务 Match 列：NEW / SUSPECTED / EXACT
Warm-Flow 底层工作流引擎。业务只保存 flow_instance_id / flow_task_id，实际流转由引擎驱动。 工作流、泳道图弹窗
泳道图 / 流程图 横轴是阶段（发起→数据准备→自动校验→匹配分流→人工治理→审批发布→追踪审计），纵轴是角色。 工作流 → Graph 泳道图

五个角色一句话

Business User发起者录入客户、上传附件、批量导入、发起变更。
BU Steward本BU治理初审、DQ复核、疑似重复处理、决定升级GC。
GC Steward全局决策跨BU证据核对、One ID关联/新建决策。
Platform Admin平台配置字段、值集、DQ规则、匹配规则、流程场景、权限。
Auditor只读审计查看所有审批轨迹、变更记录、操作日志。

5B.3 四个审批分支逐个测试（BU Steward 角色）

按钮填什么点完之后（去哪里看）客户主档最终状态
批准 意见随便填，如「BU初审通过」 ① 任务状态变 APPROVED；② 「工作流→已完成的工作流」找到这条 → 点「查看流程跟踪」弹出：11/11 步全绿；③ 步骤日志最后一步 = 审批通过（END 节点） active（生效）——成为正式 Golden Record
拒绝 必须填意见，如「注册地址与营业执照不符」 ① 任务状态变 REJECTED；② 泳道图：自动段绿色、BU 初审蓝色、后续节点终止；③ 步骤日志记录拒绝原因 rejected（已驳回）
退回补充 必须填意见，说明缺什么 ① 任务状态变 RETURNED，进入「升级与退回」清单，等申请人补材料后重新提交；② 步骤日志记录退回原因 returned（待补充）

5B.4 新建客户成功后，数据去哪了？有什么用？

保存在哪：「客户主档」页面（Business User 的「客户管理」、BU/GC 的「客户主档」、Auditor 的「客户只读查询」，都是同一张 cmd_customer 表，只是角色权限能看到/能操作的范围不同）。

什么时候成为「最终数据」：提交后 status=pending（审批中，可用）；审批通过后 status=active（正式生效）。被拒绝/退回的记录也会留在主档里并标明 rejected/returned，便于追溯。

这条数据之后的作用（对照总设计）：

  • One ID 贯穿后续工作流：客户层级维护、变更与停用、DQ 治理、查重合并、批量导入，全部以 One ID 为主键操作这条记录，而不是重新建客户；
  • 下游系统分发：active 的 Golden Record 会按集成配置分发到 SAP/CRM 等下游（「集成监控」页面可看到分发任务状态）；
  • 审计可回溯：任何一条 active 客户，都能通过 One ID 在步骤日志里还原「谁提交 → 系统检查了什么 → 谁批准的 → 什么意见」的完整证据链（Auditor 全量可查）。
图 B4：客户主档——分支演示C（退回补充）带 One ID 出现在列表中，状态列区分 active / pending / returned / rejected

说明：本次分支测试是通过接口直接驱动的，操作人记录为「BU Steward / GC Steward」；你本人在页面上操作时，操作人会记录为你的登录账号，效果一致。数据库当前保留了 4 条「分支演示A/B/C/D」数据，供你对照每个分支的最终状态。

11. 数据重置（测试后恢复种子状态）

测试多了之后数据库会乱，建议按下面的顺序清掉测试数据、重跑种子脚本。

⚠️ 危险操作：会删除业务演示数据！
仅在你确认要恢复种子状态时使用。不要对生产库执行。
  1. 停止后端（杀掉 8080 的 java 进程）。
  2. 在 MySQL 中执行： 
    DELETE FROM cmd_customer WHERE id BETWEEN 1001 AND 1099;
DELETE FROM cmd_customer_version WHERE id BETWEEN 1001 AND 1099;
DELETE FROM cmd_approval_task WHERE id BETWEEN 1001 AND 1099;
DELETE FROM cmd_approval_action WHERE id BETWEEN 1001 AND 1099;
-- 你自己的测试任务 id 可能不在这个区间，按需删除
  3. 重跑种子脚本： 
    mysql -uroot -proot ruoyi_plus < docs/cmd-poc/sql/08_业务演示数据.sql
  4. 重新启动后端 jar。

12. 常见问题

Q1：动态客户字段一片空白？

检查 Admin 平台管理里的字段是否已发布；再检查 md_field 是否有字段。此前 bug 是把 model_code 错当成 customerType 过滤，已改为固定 customerType:'All'。

Q2：OCR 识别成上海/成都/重庆，和我想的不一样？

后端按文件名匹配测试执照。确认你传的文件名和后端常量一致（如 license_06.png → 南京）。不要改文件名。

Q3：点“写回表单”没反应？

全局 OCR 弹窗写回后，结果会先暂存到共享通道，再回填到当前打开的新建客户表单。请确保你是在【新建客户申请】弹窗打开的状态下点“写回表单”。

Q4：提交申请后没反应？

此前后端 POST /cmd/customer 只 insert 不建待办/不起流程，已改为 submitApplication 完整链路。提交后应看到提示含 One ID + 申请编号，列表首位新增 Pending 记录。

Q5：升级 GC 后任务还在 BU 队列？

本次已修复。升级后任务会同步更新 scope=GC、assigneeRole=GC_STEWARD、currentNodeCode=GC_REVIEW，并从 BU 队列移到 GC 队列。

Q6：审批通过后客户状态还是 Pending？

当前 POC 尚未在审批通过时自动把 cmd_customer.status 更新为 active。这是已知缺口，后续按 V6.1 的“发布到下游”环节补齐。

Q7：服务起不来 / 8080 被占用？

先杀掉 8080 的 java 进程再启动。启动命令必须显式指定端口：
java -jar ruoyi-admin/target/ruoyi-admin.jar --server.port=8080 --server.address=0.0.0.0
