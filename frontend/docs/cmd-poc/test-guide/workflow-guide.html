0. 这套系统在干什么（业务背景）

这是一套客户主数据管理（MDM）审批工作流的演示原型。一句话：业务人员提一个"新客户开户"申请，系统先做机器校验，再走人工审批，批完后客户变成公司正式可用的"主数据"。

两个"贯穿全部页面的身份证"

名称样子含义谁生成
One IDGC-23F62B7A客户的永久身份证。客户这辈子所有记录（申请、工作流步骤、审计）都挂它提交申请时系统生成
申请编号AP-20260919-0006这一次审批流程的单号，类似快递单号提交申请时系统生成
记住：以后在任何页面，只要看到这俩号，就能"顺着线"查到这条客户的全貌。本手册全程用一条真实数据演示：One ID = GC-23F62B7A 申请编号 = AP-20260919-0006（客户名：上海清视眼镜有限公司）。

五个角色（演示里你会切换）

角色能干什么
Business User（业务）提交新客户申请、查看自己提交的客户
BU Data Steward（BU 管家）初审 BU 范围内的客户申请
GC Steward（全局管家）对"升级上来"的高风险/跨区域客户做全局决策
Auditor（审计员）只读追溯：谁、在什么时候、改了什么
Platform Admin（平台管理员）配字段 / 规则 / 模板 / Workflow（含工作流定义），看集成监控

演示系统顶部有个"模拟角色"下拉，不用真登录，直接切角色即可。

1. 登录与角色切换

步骤 1打开系统：浏览器访问 http://localhost/cmd-poc/business。默认进入 Business User 的工作台。你不用输密码，这是演示环境。
步骤 2切换角色：点击页面顶部的"模拟角色"下拉框（默认显示 Business User），选你想扮演的角色。本手册会在需要"审批"时切到 BU Data Steward。

2. 新建客户申请（OCR 识别营业执照）

步骤 3左侧菜单点 客户管理，进入客户列表页。你会看到列表里有 One ID 列，以及顶部一个可按 One ID / 申请编号 / 客户名搜索的框。
步骤 4点右上角 「新建客户」按钮，弹出申请表单。
步骤 5用 OCR 省去手抄：点表单上方的 「查看 OCR 识别结果」，弹出营业执照识别窗口。
步骤 6在 OCR 窗口选一张营业执照图片（演示里点"选择营业执照"会自动载入一张测试图），系统自动识别出：客户法定名称、统一社会信用代码、注册地址、省、市。
步骤 7点 「写回表单」，识别结果回填到申请表单，被回填的字段旁边会打 OCR回填 标签，肉眼可见。
注意：OCR 只认营业执照上有的字段。像联系人、联系电话、客户简称这类营业执照上没有的，得自己填。
步骤 8补全必填项（如联系人、联系电话、客户简称），确认无误。

3. 提交申请 · 拿到贯穿 ID

步骤 9点 「提交申请」。系统会依次自动做三件机器活：①落客户主档（同时生成 One ID）②数据质量(DQ)打分 ③智能查重。完成后弹出成功提示，里面就带着你的两个身份证。
这一步的意义：客户从"无"变成"有一条待审批的申请"。接下来所有页面都能用这两个号找到它。

4. 用 One ID 在任意页面追踪

步骤 10回到客户管理列表，在搜索框输入 GC-23F62B7A 或 AP-20260919-0006，点查询——立刻命中这条客户（此时状态是 Pending，表示审批中）。
关键能力：这个搜索框在客户管理、治理与审批、已激活工作流、已完成的工作流、流程跟踪弹窗、审计中心等所有列表都一样——也就是说你拿同一个号，能在全系统追着这条客户跑。

5. 切到 BU 角色 · 已激活工作流

步骤 11顶部把角色切成 BU Data Steward。左侧菜单展开 流程中心 → 点 「已激活工作流」。这里列出"引擎实例已启动、还没跑完的单子"。你刚提交的申请就在第一条。
菜单说明：「流程中心」下有两个菜单（RuoYi 二级子菜单样式，都是运行态视图）：
  • 已激活工作流：引擎实例已启动、还没跑完的单子（有在途实例）。点 One ID 打开泳道图，点「流程跟踪」看这一单的完整链路。
  • 已完成的工作流：已经跑完的实例列表（已批准 / 已拒绝 / 已取消 / 已完成），可按状态筛、按 One ID / 申请编号搜。
  • 流程跟踪（弹窗，不是菜单）：某一单的详情——Warm-Flow BPMN 流程图 + 11 步泳道步骤条 + 步骤明细 + Data context state + 审批轨迹。点列表行内「流程跟踪」即弹出，与「工作流定义 → 某行配置」同一形态。

6. 流程跟踪（泳道图 + 步骤明细 + 步骤日志）

步骤 12在「已激活工作流」第一条点 「流程跟踪」打开跟踪弹窗，再点弹窗里的 「泳道图」按钮（或直接点该行的 One ID），打开泳道图窗口。它把整条工作流画成泳道图：横向是阶段（提交 → 校验 → 初审 → 决策 → 完成），纵向是处理人角色。
步骤 13把窗口往下滚，看底部的 「工作流步骤执行日志」。这一步是新增的：系统把工作流每一步都记下来了，且每一步都带 One ID，所以可以精确复盘"谁、在哪个节点、做了什么"。
为什么这步重要：之前工作流"调起来"后，机器做的几步（OCR/DQ/查重）是黑盒。现在每一步都写进 cmd_workflow_step_log 表，可查、可审计。
步骤 13+从左侧 流程中心 → 已完成的工作流 进列表页：这里列出所有已结束的实例，可按状态（已批准 / 已拒绝 / 已取消 / 已完成）筛，也可按 One ID / 申请编号 / 客户主题搜。点任意一行的 「查看流程跟踪」，即弹出流程跟踪窗口（不切页、不占菜单）。
步骤 13++弹出的流程跟踪窗口与任务详情右侧按钮打开的是同一个窗口（Warm-Flow 实例流程图 + 11 步泳道步骤条 + 步骤明细 + Data context state + 审批轨迹 + 步骤日志），右下角「关闭」回到列表。点步骤条上任意一步（如「录入与附件」「OCR 与智能补全」），下方「步骤明细」面板立刻切到那一步。
入口说明（避免混淆）：「流程跟踪」有两处入口，但是同一个弹窗——①「已激活工作流」/「已完成的工作流」列表行内「流程跟踪」；② 任务 / 审批记录右侧的「流程跟踪」按钮。两处共用同一组件，展示内容完全一致，不存在两套数据或重复实现。

7. BU 审批：四个动作（核心业务）

步骤 14回到 BU 角色，进 治理与审批 菜单（也可在"已激活工作流"里直接处理）。用申请编号搜到这条，点中这一行，右侧会展开详情和四个动作按钮。
四个动作分别是什么（业务含义）：
按钮含义结果
批准BU 认可，客户资料没问题客户转 Active（正式主数据），流程结束
拒绝资料有问题，不予创建客户转 Rejected，流程终止
退回补充缺材料，打回给业务补客户转 Returned，业务可再提交
升级 GC超出 BU 权限（如跨区域/高风险）转给 GC Steward 做全局决策，BU 范围扩大为全局
步骤 15先演示最常用的 「批准」：在意见框填一句（如"OCR与DQ校验通过，同意创建"），点「批准」。
步骤 16切到 「我已处理」 标签页，能看到刚批完的这条（状态 APPROVED）。
其余三个分支怎么测：另建几条客户，分别点"拒绝 / 退回补充 / 升级 GC"即可。本演示库里已经预置了三条分支样本供你对照查看：
  • AP-20260919-0002 分支B-审批拒绝（Rejected）
  • AP-20260919-0003 分支C-退回补充（Returned）
  • AP-20260919-0001 分支A-批准通过（Approved）
想看"拒绝"分支长啥样，可在"流程中心 → 已完成的工作流"里用申请编号搜到 AP-20260919-0002，点「查看流程跟踪」弹出。

8. 审批通过后的去向

步骤 17批准后，这条客户正式成为主数据。验证三处：
  • 客户主档：用 One ID 搜，状态列变成 Active。
  • 流程跟踪：在"流程中心 → 已完成的工作流"里能看到它（状态=已完成），点「查看流程跟踪」弹出看全链路与逐步明细。
  • 业务视角：切回 Business User，客户管理列表里它从 Pending 变成 Active，业务方可以正式使用。
一句话：走完"提交 → BU 批准"，这条客户就从"申请"变成了公司里真实可用、被各系统引用的主数据。这就是工作流"吊起来"的最终目的。

9. 工作流菜单与流程跟踪弹窗

左侧 流程中心 下有两个菜单（运行态视图）：已激活工作流（引擎实例已启动、还没跑完的）、已完成的工作流（已结束实例的列表）。它们都带 One ID 列，且都能按 One ID 搜。流程跟踪不再单占菜单——点两者行内的「查看流程跟踪」即弹出窗口（单条实例的完整链路，含逐步明细），与「工作流定义 → 某行配置」同一形态。

「工作流定义」去哪了？它是配置态能力，按 V6.1 归属 Platform Admin：入口是「平台管理 → Workflow 卡片 → 管理」。业务与管家角色只跑流程、不改流程定义，所以「流程中心」菜单里不再重复放这一项。
工作流能配什么？在「工作流定义」页任选一行点【配置】，弹窗 4 个页签覆盖 V6.1 第 16 页要求的流程节点、路由条件、SLA、超时升级与邮件通知。
不能改（平台固定）：场景编码、流程编码（绑定 Warm-Flow 流程定义与引擎节点定位）、业务入口、OCR / DQ / Duplicate Check / One ID 等系统自动节点、发布与运行追踪、审计证据链，以及主干 BU 初审（不可停用）。
能改（按场景可配置）：节点路由规则可新增 / 停用（= 增删工作流项目）、命中条件表达式、办理角色、会签 or 或签、节点 SLA、场景 SLA、超时动作与超时升级、邮件通知方式与接收对象，以及 GC 决策节点是否启用（V6.1 待确认项：High End 必经、Mainstream 可只走 BU 初审）。
配置真的落库（写平台配置表），保存后重新打开仍在；图形化流程设计统一由「泳道图」承载，配置弹窗里不再重复画阶段链。
步骤 18到「流程中心 → 已完成的工作流」用 One ID / 申请编号搜到这已结束的一条，点「查看流程跟踪」弹出窗口，即实例视图：全部 11 个节点都点亮（绿色），代表流程完整跑完；点任意一步还能看该节点的明细。

10. 审计追溯（Auditor 角色）

步骤 19把角色切成 Auditor，进 审计中心。这里记录"谁、在什么时候、对哪个客户、做了什么、结果和风险等级"。每一行都带 One ID 和关联单号。
合规价值：审批动作会自动落一条审计事件（如 AE-20260919-0001），含操作前/后状态快照。监管要查"这条客户谁批的、为什么批"，用 One ID 一秒拉全。

11. 给不懂业务的人：一句话总结

  1. 业务方（Business User）：填表 → OCR 写回 → 提交。拿到 One ID 和 申请编号。
  2. 机器自动做：落档、DQ 打分、查重（这 5 步在泳道图底部步骤日志里看得见）。
  3. BU 管家在"已激活工作流"里看到在途单 → 点 One ID / 跟踪弹窗里的「泳道图」看进度 → 在"治理与审批"里点 批准/拒绝/退回/升级GC。
  4. 批准后：客户变 Active 主数据；在"流程中心 → 已完成的工作流"里能看到这条已完成实例（点「查看流程跟踪」弹出看全链路）；审计中心多一条记录。
  5. 全程：拿同一个 One ID，从客户管理、审批、工作流视图到审计，任何页面都能追到这条客户。
已支持："工作流"现为 已激活工作流 / 已完成的工作流 两个菜单，流程跟踪改为弹窗（点行内「流程跟踪」弹出，不再是单独的菜单页）；"工作流定义"已归 Platform Admin 的「平台管理 → Workflow」。列表与弹窗分工明确，弹窗与任务右侧「流程跟踪」共用同一视图，不重复、不冲突。

12. 四分支实战对照（拒绝 / 退回 / 升级 GC / 批准）

BU 初审有四个动作。第 7、8 章已演示「批准」，这里把另外三个分支（拒绝、退回补充、升级 GC）也逐一跑通并对照。四个分支的差异集中体现在 客户主档最终状态 与 泳道图节点的收尾形态 上。

12.1 四个动作 → 结果一览表

动作按钮样式客户主档状态流程终态泳道图收尾形态
批准批准Active已完成11/11 全绿，末节点「生成/合成 One ID」变绿
拒绝拒绝Rejected终止已过节点绿，当前/后续节点变灰或 stopped，拒绝边画成虚线
退回补充退回补充Returned回到业务流程回到起点，业务可修改后再次提交
升级 GC升级 GC保持 Pending转 GC 决策范围从 BU 扩大为全局，末节点「GC Scope 决策」变蓝（当前）

12.2 分支一：拒绝（Rejected）

步骤 20BU 角色 → 治理与审批，用申请编号搜到待办，点中该行。
步骤 21在右侧详情点 「拒绝」，意见框填写拒绝理由（如"证照与申报主体不一致"），确认。
步骤 22到「流程中心 → 已完成的工作流」用同一申请编号搜到它，点「查看流程跟踪」弹出看拒绝分支的收尾。
验证点：客户主档状态应为 Rejected；审计中心会新增一条「拒绝」事件。

12.3 分支二：退回补充（Returned）

步骤 23另取一条待办，点 「退回补充」，填写需要补齐的材料（如"请补充门店授权书"）。
步骤 24客户转 Returned，业务角色在客户管理里能看到它、修改后重新提交，流程重新从「创建客户申请」开始。

12.4 分支三：升级 GC（Escalated）

步骤 25选一条超出 BU 权限的待办（如跨区域 / 高风险），点 「升级 GC」。
步骤 26该记录从 BU 队列转入 GC 队列：切到 GC Steward 角色 → 全局治理决策，即可看到它，由 GC 做最终合并 / 创建决策。
四分支小结：同一个申请，因初审动作不同，会走向 4 条完全不同的终态。贯穿全过程的仍是同一个 One ID 与 申请编号——用它们在「流程跟踪」弹窗里可以随时复查每条分支的真实走向。

13. 提交出错提示与常见报错

系统对必填项、格式、验证码等都有前端校验，出错时会就地红字提示，不会把脏数据写进库。下面演示最常见的"必填项漏填"。

步骤 27Business User → 客户管理 → 点「新建客户」，不填任何内容直接点「提交申请」。
常见报错速查：
  • 必填项为空 → 字段下方红字「请输入 XXX」，提交被拦截。
  • 验证码错误（登录页）→ 「验证码错误，请重新输入」，并自动刷新验证码。
  • OCR 未识别就提交 → 核心字段仍为空 → 触发必填校验；即便提交，DQ 也会因缺字段扣分、风险等级升高。
  • 重复客户 → 系统查重命中后给出疑似重复提示，需走合并 / 关联流程，而非直接新建。
设计原则：能在前端拦住的错误绝不放到后端；前端没拦住的，后端 DQ 规则会再兜一层，并把风险等级透出到泳道图与审批列表。
